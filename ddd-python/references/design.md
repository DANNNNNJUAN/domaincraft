# 从业务规则到对象设计

简体中文 · [English](design.en.md)

先写清业务事实和不变量，再确定上下文、聚合、对象职责和行为契约。遇到具体的变化或协作问题时，比较实现方式，最后用测试检查这个决定。

判断行为归属时，看看哪个对象掌握所需信息，也看看状态的生命周期、权威来源和业务含义。每个重要决定都应能回答：它维护什么规则，为什么放在这里，有哪些替代方案，怎样验证？

## 什么时候需要模式

| 已经遇到的问题 | 可以考虑的实现 | 需要检查的契约 |
|---|---|---|
| 一条简短的业务规则 | 普通方法或函数 | 输入、结果和异常 |
| 多种需要替换的算法 | 函数策略或 Strategy 对象 | 各实现的输入、结果与错误语义一致 |
| 可复用、可组合的条件 | 函数组合或 Specification | AND/OR/NOT 的含义与副作用 |
| 创建过程复杂，且必须保证初始状态合法 | 命名构造方法或 Factory | 每个公开创建入口都遵守初始约束 |
| 外部协议与业务语言不同 | 端口与 Adapter | 转换、错误和重试语义 |
| 状态相关行为复杂且持续增加 | 显式状态表或 State | 所有入口都拒绝非法状态转换 |

Python 的函数、闭包和 Protocol 往往能减少样板代码。值对象的成员也应不可变：`dataclass(frozen=True)` 只限制字段赋值，不会冻结字段里的列表等对象。业务约束仍需运行时校验。

## 用 SOLID 审视实现

- **SRP：**谁会提出这项变化？业务计算、数据库映射和网络协议是否挤在同一处？必须共同维护的不变量应留在一起。
- **OCP：**扩展点对应什么已知变化？先找到变化证据，再增加抽象。
- **LSP：**替换实现后，原来合法的输入、承诺的结果和不变量仍然成立吗？使用同一组黑盒契约测试，包含失败行为。
- **ISP：**接口应包含调用者实际需要的操作。
- **DIP：**按选定架构检查依赖方向。业务端口由用途决定，装配层的例外通过决策记录说明。

## 注释与评审

模块文档说明上下文和职责；公共对象与重要方法说明业务含义、前置条件、结果、副作用和异常。用 `Rules: ORD-001, ORD-002` 将注释关联到规则；规则是否满足仍由行为测试验证。

不显然的参数可以放进 `Args:`。本地检查会核对列出的参数名，注释内容的准确性由评审确认。私有方法按需要说明即可。

评审批注应指出位置、问题和业务影响，给出规则或决策依据，再提出修改建议与验证方式。静态检查无法确认的部分标为需评审。

## 订单示例覆盖什么

随包示例包含订单封装、Money 值对象、领域异常、应用编排、Repository Protocol，以及共享同一仓储契约的内存和 SQLite 实现。当前确认规则由普通方法完成。

库存并发、分布式支付、Outbox 和补偿流程需要各自的设计与集成测试。涉及这些需求时，在现有契约上补充相应的一致性验证。
